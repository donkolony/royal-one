## 1. Conventions

### 1.1 Base URL and versioning

| Environment | Base URL |
|---|---|
| Local | `http://localhost:8000/api/v1` |
| Hosted (Render) | `https://<backend-host>/api/v1` — **TBD**, set as `VITE_API_URL` on the frontend |

- All endpoints except `GET /health` live under `/api/v1`.
- Breaking changes will go to `/api/v2`. Additive changes (new optional fields, new endpoints) stay in `v1`. **Frontend code must ignore unknown fields.**
- Interactive docs: `GET /docs`. Machine-readable schema: `GET /openapi.json` (FastAPI defaults).

### 1.2 Format

| Topic | Rule |
|---|---|
| Content type | `application/json; charset=utf-8` for requests and responses. File uploads use `multipart/form-data` (Section 5.10 and 5.11). |
| Field names | `snake_case`. Enum values are lowercase `snake_case` strings. |
| Spelling | Identifiers use `advisor` (matches PRD role names). UI copy may say "adviser", which is the Royal Square spelling. |
| IDs | UUID v4 strings. Never hardcode IDs; they are generated by the seed script. |
| Timestamps | ISO 8601 in UTC with a trailing `Z`: `2026-09-19T14:30:00Z`. Convert to `Africa/Johannesburg` (SAST, UTC+2) for display. |
| Dates | `YYYY-MM-DD`, no time zone. Used for `due_date`, `target_date`, `renewal_date`, etc. |
| Money | Integer **cents** in fields ending `_cents`. Currency is always ZAR in v1. `12500000` means R 125 000.00. Never floats. |
| Nulls | Optional values are returned as `null`, never omitted, so shapes are stable. In **requests**, omit a field to leave it unchanged (PATCH) or use `null` to clear it. |
| Booleans | JSON `true` / `false`. |
| Empty collections | `[]`, never `null`. |
| Unknown fields in a request | Rejected with `422 validation_error` (`code: "extra_forbidden"`). |

### 1.3 Lists and pagination

Every list endpoint returns the same envelope:

```json
{ "items": [ /* ... */ ], "total": 42, "limit": 25, "offset": 0 }
```

| Query param | Default | Rules |
|---|---|---|
| `limit` | `25` | 1 to 100 |
| `offset` | `0` | ≥ 0 |
| `sort` | endpoint-specific | `field` ascending or `-field` descending. Only fields listed for the endpoint are accepted, otherwise `422`. |

Small static collections (insurers, checklist, request types) return `{ "items": [...] }` with no paging fields.

### 1.4 Errors

Every non-2xx response has this body. FastAPI's default `{"detail": ...}` shape is **replaced**, so the frontend only needs to handle one shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "One or more fields are invalid.",
    "details": [
      { "field": "incident.description", "code": "too_short", "message": "Describe what happened in at least 10 characters." }
    ],
    "request_id": "9f3c2b1e-6d1a-4c1f-9d55-0c6c2f3e7a10",
    "retry_after_seconds": null
  }
}
```

- `details` is present for `validation_error` only. `field` is a dotted/bracketed path, e.g. `witnesses[0].phone`.
- `retry_after_seconds` is present for `rate_limited` and `llm_unavailable` only (also sent as the `Retry-After` header).
- `message` is safe to show to a user for 4xx codes except where stated. For 5xx, show your own generic message and log `request_id`.
- Every response (success or error) carries an `X-Request-ID` header. If the client sends `X-Request-ID` (≤ 64 chars, `[A-Za-z0-9-]`), the server reuses it. Quote it in bug reports.

| HTTP | `error.code` | When |
|---|---|---|
| 400 | `bad_request` | Malformed JSON or unreadable multipart body. |
| 401 | `unauthenticated` | No `Authorization` header. |
| 401 | `token_invalid` | Token is malformed, unverifiable, or the user no longer exists. Sign the user out. |
| 401 | `token_expired` | Access token expired. Refresh the Supabase session and retry once. |
| 403 | `forbidden` | Authenticated, but the role may not call this endpoint (e.g. a client calling an adviser-only route). |
| 404 | `not_found` | Resource does not exist **or is outside the caller's scope** (see 2.3). |
| 409 | `invalid_state_transition` | Action not allowed in the resource's current state (e.g. submit an already-submitted claim). |
| 409 | `conflict` | Other state conflicts (e.g. deleting a rule-generated reminder). |
| 413 | `payload_too_large` | Upload exceeds the size limit. |
| 415 | `unsupported_media_type` | File type not allowed, or the file content does not match its declared type. |
| 422 | `validation_error` | Body or query failed validation. See `details`. |
| 429 | `rate_limited` | Too many requests (assistant and email-draft endpoints only in v1). |
| 500 | `internal_error` | Unexpected server error. |
| 501 | `not_implemented` | Reserved route not built in this release (P2 endpoints). |
| 502 | `upstream_error` | Supabase or another dependency failed. |
| 503 | `llm_unavailable` | The LLM provider failed or is rate-limited **and** the fallback provider also failed. Retry after `retry_after_seconds`. |

### 1.5 HTTP status conventions

| Verb | Success |
|---|---|
| `GET` | `200` |
| `POST` that creates | `201` with a `Location` header and the created object |
| `POST` that performs an action | `200` with the updated object |
| `PATCH` | `200` with the updated object |
| `PUT` | `200` with the resulting object |
| `DELETE` | `204`, empty body |

### 1.6 CORS and headers

- Allowed origins are set server-side via `ALLOWED_ORIGINS`. The frontend must call from one of those exact origins.
- Authentication uses the `Authorization` header, not cookies, so `credentials: 'include'` is not needed.
- Allowed request headers: `Authorization`, `Content-Type`, `X-Request-ID`. Exposed response headers: `X-Request-ID`, `Retry-After`, `Location`.

### 1.7 Caching **(proposal)**

`GET /meta` (no login needed) sends `Cache-Control: public, max-age=3600`. The other static reference endpoints (`GET /insurers`, `GET /claims/checklist`, `GET /requests/types`) need a login, so they send `Cache-Control: private, max-age=3600`. Every other response sends `Cache-Control: no-store`. The checklist is intentionally cacheable so a PWA can show it with poor connectivity at an accident scene.

### 1.8 Rate limits **(proposal)**

`POST /assistant/query` and `POST /email/drafts/generate`: default 10 requests per minute per user (configurable via env). Exceeding it returns `429 rate_limited`. Other endpoints are not rate limited in v1.

### 1.9 Not in v1 (do not build UI that depends on these)

- Outbound email, SMS or push notifications. Reminders are **in-app only**.
- Sending email. The assistant drafts; a human sends elsewhere. There is no send endpoint.
- Live Gmail (OAuth). Email endpoints run on a simulated adapter (Section 5.14).
- Real insurer integrations, e-signing, payments.
- WebSockets or server push. Use polling or refetch-on-focus (Section 7.4).
- Admin endpoints and uploading documents into the RAG library over the API.
- Languages other than English.

## 2. Authentication, roles and scoping

### 2.1 Login

**There is no login endpoint on this API.** The frontend signs users in with the Supabase Auth client (email/password or magic link, per `TECHSTACK.md`) and sends the resulting **access token** to this API:

```http
GET /api/v1/me HTTP/1.1
Authorization: Bearer <supabase_access_token>
```

The backend never sees passwords. The frontend only ever holds the Supabase URL and the **anon/publishable** key; the service-role key never leaves the backend.

### 2.2 Roles

| Role | Description |
|---|---|
| `client` | A policyholder. |
| `advisor` | A financial adviser. Sees only the clients assigned to them. |
| `admin` | **Future.** Not present in v1. |

The role comes from the server-side `profiles` table and is returned by `GET /me`. It is **never** read from token claims that a user can edit (such as `user_metadata`). After login, the frontend must call `GET /me` and route by `role`.

In v1 every client and adviser has a login, so `client.id` and `advisor.id` **equal** the Supabase auth user id.

### 2.3 Scoping (who can see what)

The same route serves both roles; the result is scoped by who is calling.

| Caller | Sees |
|---|---|
| `client` | Only rows belonging to themselves. |
| `advisor` | Only rows belonging to clients where `client.adviser_id = advisor.id`. |

- A resource outside the caller's scope returns **`404 not_found`, not 403**, so IDs cannot be probed.
- An action the caller's *role* may never perform returns `403 forbidden` (e.g. a client calling `POST /goals`).
- Advisers pass `client_id` as a query parameter to narrow list endpoints. For a client, `client_id` is ignored if it equals their own id and returns `404` if it is anyone else's.
- **Draft claims are private to the client.** Advisers never see a claim while its status is `draft` (list, pipeline and detail all exclude it).

### 2.4 Permission matrix

`own` = the client's own data. `assigned` = the adviser's assigned clients. `—` = `403`.

| Capability | Endpoint(s) | Client | Advisor |
|---|---|---|---|

## 3. Enumerations and reference data

All of these are also returned by `GET /meta` so the frontend does not have to hardcode them. Labels are English.

### 3.1 Claim status (`ClaimStatus`)

Statuses are ordered. A claim only moves one step forward (or one step back, adviser only). Labels differ by role: `client_label` is plain and reassuring, `advisor_label` is efficient.

| # | `value` | `client_label` | `advisor_label` | PRD step (§4.4 C) | Who moves it here |
|---|---|---|---|---|---|
| 0 | `draft` | Not sent yet | Draft (not visible) | — | Client (`POST /claims`) |
| 1 | `submitted` | Sent to Royal Square | Submitted | — | Client (`/submit`) |
| 2 | `registered` | Registered with your insurer | Registered (claim no. issued) | 1 | Adviser |
| 3 | `assessment` | Vehicle assessment | Assessment | 2, 3 | Adviser |
| 4 | `quotes` | Repair quotes | Quotes with insurer | 4 | Adviser |
| 5 | `authorised` | Repairs approved | Authorised | 5, 6 | Adviser |
| 6 | `in_repair` | Being repaired | In repair | 7, 8 | Adviser |
| 7 | `completed` | Repairs finished | Completed, awaiting client sign-off | 9 | Adviser |
| 8 | `closed` | Closed | Closed | 10 | Client (`/review`) or adviser |

Transition rules:

- Forward: `n → n+1` only. `draft → submitted` is done by `POST /claims/{id}/submit`. `completed → closed` is done by `POST /claims/{id}/review` (client) or `POST /claims/{id}/transitions` (adviser).
- Back: adviser may move one step back (to correct a mistake), except into or out of `draft`, and never out of `closed`.
- `submitted → registered` requires `insurer_details.claim_number` to be set (PRD step 1: the insurer returns the claim number).
- Every transition writes a timeline event.
- The claim response includes `allowed_transitions` for the calling role, so the UI does not need to compute this.

Hire car (`HireCarStatus`), tracked separately from status, because it runs alongside repair (PRD steps 7 and 9): `not_required` (default), `requested`, `arranged`, `delivered` (delivered to the repairer), `return_arranged`, `returned`.

### 3.2 Reminder types (`ReminderType`)

Lead times and rules are **(proposal)** except the examples that come from PRD §4.2.

| `type` | Label | Default audience | Generated from | `lead_days` |
|---|---|---|---|---|
| `valuation_certificate` | Valuation certificate due | `both` | `policy.valuation_certificate_date` + 2 years | 30 |
| `licence_expiry` | Driving licence expiring | `client` | `client.drivers_licence_expiry` | 60 |
| `annual_review` | Annual financial review | `advisor` | `client.last_annual_review_date` + 1 year | 30 |
| `retirement_fee_renewal` | Retirement fee renewal | `advisor` | `policy.renewal_date` where `category = retirement` | 30 |
| `birthday` | Client birthday | `advisor` | next occurrence of `client.date_of_birth` | 7 |
| `anniversary` | Client anniversary | `advisor` | next occurrence of `client.client_since` **(requires confirmation: PRD does not define "anniversary")** | 7 |
| `claim_police_report` | Report to police within 48 hours | `client` | claim `police.report_deadline_at` while `police.reported` is not `true` and the claim is `draft` or `submitted` | 2 (the deadline is at most two days away, so the reminder shows as soon as the claim is started) |
| `custom` | Custom reminder | any | manual (`POST /reminders`) | — |

`lead_days`: a rule-generated reminder appears once `due_date − today ≤ lead_days`, and only if it is not more than 90 days overdue (so stale data does not flood the list). Birthday and anniversary reminders are for the *next* occurrence, so once the day passes an unactioned one is dismissed automatically. The PRD says "the list of reminder types will keep growing"; new types are added server-side and appear in `GET /meta`. **The frontend must render unknown `type` values gracefully** (fall back to `title`).

### 3.3 Request types (`RequestType`) — PRD §4.5

`address_change`, `bank_details_change`, `policy_document`, `border_letter`, `irp5`, `consultation`, `client_information`. Full field definitions: `GET /requests/types` and Section 5.11.

Request status (`RequestStatus`): `submitted` → `in_progress` → `completed` or `declined`. (`submitted` may also go straight to `completed` or `declined`.)

### 3.4 Policy

`PolicyCategory` **(proposal, derived from PRD §1 and §4.2; requires confirmation)**: `motor`, `life`, `health`, `funeral`, `personal_other`, `commercial`, `investment`, `retirement`.

`PolicyStatus`: `active`, `pending`, `lapsed`, `cancelled`.

### 3.5 Financial items and goals

`FinancialItemKind`: `asset`, `liability`.
`FinancialItemCategory` **(proposal)**:
- assets: `property`, `vehicle`, `cash`, `investments`, `retirement`, `business`, `other_asset`
- liabilities: `home_loan`, `vehicle_finance`, `credit_card`, `personal_loan`, `other_liability`

`GoalCategory` **(proposal)**: `retirement`, `education`, `property`, `emergency_fund`, `travel`, `debt_repayment`, `other`.
`GoalStatus`: `active`, `achieved`, `archived`.
`GoalType`: `individual`, `shared` (derived: more than one participant).

### 3.6 Attachments (`AttachmentKind`)

| `kind` | Used for (PRD §4.4) | Allowed content types |
|---|---|---|
| `road_photo` | Road surface and direction of travel | image |
| `vehicle_photo` | Vehicles involved | image |
| `people_photo` | People involved | image |
| `plate_or_disc_photo` | Licence plates, registration discs | image |
| `id_document` | ID documents of everyone involved | image, `application/pdf` |
| `witness_voice_note` | Optional witness voice note | audio |
| `drivers_licence` | Driver's licence | image, `application/pdf` |
| `accident_sketch` | Sketch of the accident | image (PNG/JPEG exported from a canvas) |
| `other` | Anything else (also used on requests) | image, `application/pdf` |

Limits **(proposal, configurable, always read the live values from `GET /meta` → `attachment_rules`)**:

- image: `image/jpeg`, `image/png`, `image/webp` (HEIC/HEIF **not** accepted in v1; the frontend must send JPEG/PNG/WebP)
- document: `application/pdf`
- audio: `audio/webm`, `audio/mp4`, `audio/mpeg`, `audio/ogg`, `audio/wav` (requires confirmation against what browsers actually record)
- max 10 MB per file, max 40 attachments per claim, max 5 per request
- The server checks the file's **content signature**, not only the `Content-Type` header.

### 3.7 Documents

`DocumentCategory`: `policy_wording`, `internal_process`, `company_policy`, `regulation`. `DocumentStatus`: `indexed`, `processing`, `failed`.

### 3.8 Email

`EmailFlagCode` (deterministic rules only in v1): `insurer_sender`, `client_sender`, `claim_reference_match`, `deadline_keyword`.

## 4. Shared types (TypeScript notation)

These are a contract description, not code the backend ships. `?` never means "omitted"; it means "may be `null`" (see 1.2).

```ts
type UUID = string;
type ISODate = string;      // "2026-09-19"
type ISODateTime = string;  // "2026-09-19T14:30:00Z"
type Role = 'client' | 'advisor';

interface Page<T> { items: T[]; total: number; limit: number; offset: number }

interface FieldError { field: string; code: string; message: string }
interface ApiError {
  error: {
    code: string;                       // see 1.4
    message: string;
    details?: FieldError[];             // validation_error only
    request_id: string;
    retry_after_seconds?: number | null;
  };
}

// ---- people ----
interface PersonRef { id: UUID; full_name: string; email: string; phone: string | null }

interface Profile {                       // GET /me
  id: UUID;
  email: string;
  full_name: string;
  role: Role;
  phone: string | null;
  created_at: ISODateTime;
  client: ClientProfile | null;           // present when role = 'client'
  advisor: { id: UUID } | null;           // present when role = 'advisor'
}

interface ClientProfile {
  id: UUID;
  adviser: PersonRef | null;              // the client's assigned adviser
  date_of_birth: ISODate | null;
  drivers_licence_expiry: ISODate | null;
  client_since: ISODate | null;
  last_annual_review_date: ISODate | null;
}

interface ClientSummary { id: UUID; full_name: string; email: string; phone: string | null }

interface ClientDetail extends ClientSummary {   // advisor view
  date_of_birth: ISODate | null;
  drivers_licence_expiry: ISODate | null;
  client_since: ISODate | null;
  last_annual_review_date: ISODate | null;
  counts: { policies: number; open_claims: number; active_goals: number; pending_requests: number; pending_reminders: number };
  created_at: ISODateTime;
}

// ---- reference ----
interface Insurer { id: UUID; name: string }

// ---- policies ----
interface Policy {
  id: UUID;
  client_id: UUID;
  insurer: Insurer;
  category: PolicyCategory;
  product_name: string;                   // e.g. "Comprehensive vehicle cover"
  policy_number: string;
  status: PolicyStatus;
  asset_description: string | null;       // e.g. "2021 VW Polo, CA 123-456" (motor)
  cover_amount_cents: number | null;
  current_value_cents: number | null;     // investment / retirement products
  premium_cents: number | null;
  premium_frequency: 'monthly' | 'annual' | null;
  start_date: ISODate | null;
  renewal_date: ISODate | null;
  valuation_certificate_date: ISODate | null;   // date of the last certificate
}

// ---- net worth ----
interface NetWorth {
  currency: 'ZAR';
  total_assets_cents: number;
  total_liabilities_cents: number;
  net_worth_cents: number;                // assets - liabilities (may be negative)
  as_of: ISODate;                         // date the figure was computed
  breakdown: {
    kind: FinancialItemKind;
    category: FinancialItemCategory;
    source: 'balance_sheet' | 'policy';
    total_cents: number;
  }[];
}

interface FinancialItem {
  id: UUID;
  client_id: UUID;
  kind: FinancialItemKind;
  category: FinancialItemCategory;
  label: string;
  amount_cents: number;                   // positive; kind determines the sign
  as_of_date: ISODate;
  updated_at: ISODateTime;
}

// ---- goals ----
interface Goal {
  id: UUID;
  title: string;
  description: string | null;
  category: GoalCategory;
  type: GoalType;
  status: GoalStatus;
  target_amount_cents: number;
  current_amount_cents: number;
  progress_percent: number;               // 0-100, one decimal, capped at 100
  target_date: ISODate | null;
  participants: { client_id: UUID; full_name: string }[];   // 1 = individual, >1 = shared
  created_by: UUID;
  created_at: ISODateTime;
  updated_at: ISODateTime;
}

// ---- reminders ----
interface Reminder {
  id: UUID;
  type: ReminderType | string;            // render unknown types via title
  title: string;
  description: string | null;
  due_date: ISODate;
  audience: 'client' | 'advisor' | 'both';
  status: 'pending' | 'done' | 'dismissed';
  urgency: 'overdue' | 'due_soon' | 'upcoming';   // computed: overdue = past due; due_soon = within 7 days
  source: 'rule' | 'manual';
  client: { id: UUID; full_name: string };
  related: { resource: 'policy' | 'claim' | 'client'; id: UUID } | null;
  completed_at: ISODateTime | null;
  created_at: ISODateTime;
}

// ---- claims ----
interface Witness { name: string; phone: string | null; email: string | null; statement: string | null }

interface ThirdParty {
  name: string;
  phone: string | null;
```

### 5.7 Net worth and financial items

Net worth is **not** a live external feed (PRD §9 excludes it). In v1 it is:

> `net_worth = Σ assets − Σ liabilities`, where assets and liabilities are the adviser-maintained `financial_items`, **plus** the `current_value_cents` of the client's `active` `investment` and `retirement` policies (reported in `breakdown` with `source: "policy"`).

Advisers must not enter a policy's value again as a financial item (double counting). **(proposal; requires confirmation with Royal Square.)**

#### `GET /net-worth` — P1
Auth: any role, scoped. Query: `client_id` (advisor, required). `200`: `NetWorth`.

### 5.8 Goals

Progress is `min(100, round(current / target × 100, 1))`.

#### `GET /goals` — P0
Auth: any role, scoped. Query: `client_id` (advisor), `status` (default `active`; `all` allowed), `limit`, `offset`, `sort` (`target_date` default, `-updated_at`).
`200`: `Page<Goal>`. A shared goal appears for every participant.

#### `GET /goals/{goal_id}` — P1
`200`: `Goal`.

#### `POST /goals` — P0
Auth: `advisor`. Creates an individual goal (one client) or a shared goal (several clients).
```json
{
  "client_ids": ["0b7e…", "7d91…"],
  "title": "Children's university fund",
  "description": "Shared goal for the household",
  "category": "education",

  "current_amount_cents": 15000000,

```
Rules: `client_ids` 1 to 5 distinct assigned clients; `title` 1 to 120 chars; `target_amount_cents` > 0; `current_amount_cents` ≥ 0 (default 0); `target_date` today or later (optional).
`201`: `Goal`.

#### `PATCH /goals/{goal_id}` — P0
Auth: `advisor`. Editable: `title`, `description`, `category`, `target_amount_cents`, `current_amount_cents`, `target_date`, `status` (`active` or `archived`), `client_ids` (replaces participants).
Side effect: when `current_amount_cents ≥ target_amount_cents` and status is `active`, the server sets status `achieved`. `200`: `Goal`.

#### `DELETE /goals/{goal_id}` — P2
Auth: `advisor`. Archives the goal (`status = archived`). `204`.

### 5.9 Reminders

**How reminders are produced.** Rule-based reminders (Section 3.2) are **computed on read**: every `GET /reminders` and dashboard call first runs an idempotent evaluation for the clients in scope and creates any reminder that is inside its `lead_days` window and does not already exist. There is no background scheduler. Manual reminders are created by advisers. Reminders are in-app only (1.9).

#### `GET /reminders` — P0
Auth: any role, scoped. A client sees only `audience` = `client` or `both`. An adviser sees all audiences for assigned clients.

Query: `status` (`pending` default, `done`, `dismissed`, `all`), `type`, `audience` (advisor only), `client_id` (advisor), `urgency`, `due_from`, `due_to` (dates, inclusive), `limit`, `offset`, `sort` (`due_date` default, `-due_date`).
`200`: `Page<Reminder>`.

```json
{ "items": [ {
  "id": "e10a…", "type": "licence_expiry", "title": "Your driving licence expires on 30 Nov 2026",
  "description": "Renew it before it expires to stay covered while driving.",
  "due_date": "2026-11-30", "audience": "client", "status": "pending", "urgency": "upcoming", "source": "rule",
  "client": { "id": "0b7e…", "full_name": "Demo Client One" },
  "related": { "resource": "client", "id": "0b7e…" },
  "completed_at": null, "created_at": "2026-09-19T14:30:00Z"
} ], "total": 1, "limit": 25, "offset": 0 }
```

#### `POST /reminders` — P1
Auth: `advisor`. Creates a manual reminder.
```json
{ "client_id": "0b7e…", "type": "custom", "title": "Call about fund switch", "description": null, "due_date": "2026-10-05", "audience": "advisor" }
```
`type` must be `custom` or any type from `GET /meta` (manual creation of a typed reminder is allowed). `due_date` may be in the past (becomes `overdue`). `201`: `Reminder`.

#### `PATCH /reminders/{reminder_id}` — P1
Auth: `advisor`. Editable: `title`, `description`, `due_date`, `audience`, `status` (`pending`, `dismissed`). `200`: `Reminder`.

#### `POST /reminders/{reminder_id}/complete` — P0
Auth: client (own, audience `client`/`both`) or advisor (assigned). No body. Sets `status = done`, `completed_at = now`. Already done → `409 invalid_state_transition`. `200`: `Reminder`.

#### `DELETE /reminders/{reminder_id}` — P2
Auth: `advisor`. Only `source = manual`; rule-generated reminders return `409 conflict` (dismiss them with `PATCH`). `204`.

#### `POST /reminders/run-check` — P1
Auth: `advisor`. Forces the evaluation for all assigned clients (useful in the demo to show automation on demand). No body.
`200`: `{ "evaluated_clients": 3, "created": 4, "already_existing": 7 }`.

### 5.13 Assistant (RAG, adviser only)

Answers questions **only** from the approved documents, with citations to document and page (PRD §5.1). It is a document-search assistant, not a source of advice, and the UI should say so.

#### `POST /assistant/query` — P0
Auth: `advisor`. Rate limited (1.8).

Request:
```json
{
  "question": "What is the notification period for a motor claim?",
  "conversation_id": null,
  "filters": { "category": ["policy_wording"], "insurer_id": null, "document_ids": [] }
}
```
| Field | Rules |
|---|---|
| `question` | 3 to 1000 chars. |
| `conversation_id` | `null` starts a new conversation; an existing id continues it (follow-ups use the earlier turns as context). Must belong to the caller. |
| `filters` | Optional. All three keys optional. Restricts which documents may be searched. |

Response `200` (grounded):
```json
{
  "conversation_id": "5d2e…", "message_id": "9a0b…",
  "answer": "The demo policy wording asks the insured to notify the insurer within 30 days of the event [1]. The internal claims process also requires the adviser to log the claim the same day [2].",
  "grounded": true,
  "citations": [
    { "index": 1, "document_id": "d001…", "document_title": "Demo Motor Policy Wording", "category": "policy_wording", "is_synthetic": true, "page": 12, "quote": "The insured must notify the insurer of any event likely to give rise to a claim within 30 days…" },
    { "index": 2, "document_id": "d002…", "document_title": "Demo Claims Handling Process", "category": "internal_process", "is_synthetic": true, "page": 3, "quote": "Log every new claim in the register on the day it is received…" }
  ],
  "model": { "provider": "groq", "name": "<configured model>" },
  "latency_ms": 1840
}
```
Response `200` (nothing relevant found): the server does **not** guess.
```json
{
  "conversation_id": "5d2e…", "message_id": "9a0c…",
  "answer": "I couldn't find this in the approved documents. Try rephrasing, or check the document library.",
  "grounded": false, "citations": [],
  "model": { "provider": "groq", "name": "<configured model>" }, "latency_ms": 620
}
```

Contract guarantees (the backend must enforce these; the frontend can rely on them):
1. `grounded: true` ⇒ at least one citation.
2. Every `[n]` marker in `answer` has a matching `citations[].index`, and every citation is referenced at least once.
3. `quote`, `document_title` and `page` come from the stored source chunk, **never from model output**. Citations that cannot be matched to a retrieved chunk are dropped, and if none remain the answer is replaced by the `grounded: false` refusal.
4. `answer` is a Markdown subset: paragraphs, `-` lists, `**bold**`. **No raw HTML.** The frontend must still sanitise it.
5. Document text is treated as data, not instructions (prompt-injection defence): instructions inside a document do not change assistant behaviour.
6. Example answer values above are illustrative and use synthetic wording. **They are not statements about any real insurer's policy.**

Errors: `429 rate_limited`; `503 llm_unavailable` (both providers failed, or none is configured, and the question had relevant passages; retry after `retry_after_seconds`); `422` (bad filters); `404` (`conversation_id` unknown or not yours).

Behaviour worth knowing: a question with **no relevant passage never calls the model** and answers with the `grounded: false` refusal, so it still works when the LLM is down or unconfigured. When no LLM is configured, `model` is `{ "provider": "none", "name": "" }` on such a refusal. Malformed model output is retried once and then also becomes the refusal (not an error). A very short follow-up (two or fewer keywords) borrows the terms of the previous question in the conversation for retrieval.

### 5.15 Audit trail (staff)

Added with the Revenue & Compliance work (`docs/AUDIT.md`). `staff` = adviser or owner. The owner sees every entry; an adviser sees entries about their assigned clients plus their own actions. A client gets `403`.

Every meaningful event is appended by the service layer in the same transaction as the change: claim, request, document, goal, reminder, policy, balance-sheet and client edits, staff views of a client or claim (repeat views within 10 minutes are collapsed), AI assistant queries, AI email drafts, and refused attempts to open another adviser's record (`access.denied`). Summaries and details never contain document text, bank numbers or email bodies.

| Endpoint | Notes |
|---|---|
| `GET /audit` | Newest first, paged. Filters: `client_id`, `actor_id`, `action` (exact, or a prefix such as `claim`), `entity_type`, `date_from`, `date_to` (inclusive, South African dates), `q` (text in the summary). |
| `GET /audit/export` | The same filters, as `text/csv` (at most 10 000 rows, oldest first). Cells that could be read as spreadsheet formulas are prefixed with an apostrophe. The export is itself logged as `audit.exported`. |
| `GET /audit/verify` | Owner only. Recomputes the SHA-256 hash chain: `{ok, checked, first_bad_id, head}`. |

```ts
interface AuditEntry {
  id: number; occurred_at: ISODateTime;
  actor: { id: UUID | null; full_name: string | null; role: "client" | "advisor" | "owner" | "system" };
  action: string; entity_type: string; entity_id: string | null;
  client: { id: UUID; full_name: string } | null;
  summary: string; details: Record<string, unknown>;
  ip: string | null; user_agent: string | null; request_id: string | null; hash: string;

```

**Tamper evidence is demo level.** The database refuses UPDATE, DELETE and TRUNCATE on `audit_log`, and each row stores the hash of its content and of the previous row. A database administrator could still drop the triggers; verification then reveals an edited row but cannot prevent one.

### 5.16 Opportunity Radar (staff)

A ranked, explainable feed of commercial opportunities. **Detection is rules on data** (`backend/app/services/radar.py`), not a model: under-insurance, goals behind schedule, life events (recorded events, retirement approaching, policy renewals), missing cover categories, lapsed cover, single-product clients, expiring documents. Detection runs when the list, summary or a card is read and is idempotent (a `dedupe_key` makes the same fact surface once).

Every opportunity carries the **evidence** (the actual numbers and fields that triggered it), a `value_formula`, and `is_demo_estimate: true`. **All rand figures are demo estimates** from one config file (`backend/app/domain/radar_config.py`), served by `GET /opportunities/assumptions` for the "How is this calculated?" tooltip. They are placeholders, not real commission rates or premiums.

`staff` = adviser or owner. An adviser sees opportunities for their assigned clients; the owner sees all of them **read-only**. Only the client's adviser can act (the owner gets `403`). A client gets `403` on every route. An opportunity outside the caller's scope is `404` and the attempt is written to the audit trail.

### 5.17 Business Health (owner) and client health

Owner only (`403` for everyone else). Every tile answers "where is money made or lost?" and every number drills down: each tile carries a `drilldown` key, and `GET /owner/drilldown?metric=<key>` returns the records behind it (`{metric, total, items[{client, adviser, detail, value_cents, link:{path}}], value_cents}`). **A tile's count always equals `total` of its drill-down** (asserted by tests). `link.path` is relative to the staff area (`/clients/{id}`, `/claims/{id}`, `/radar?client={id}`, `/clients/{id}?tab=compliance`).

`GET /owner/business-health` returns: `top_actions` (three, ranked by urgency tier then value; the rule is in `top_actions_rule`), `revenue_at_risk` (total, reasons: lapsed, review overdue, claims stuck, identity expiring), `revenue_opportunity` (open value by adviser and by signal, with lifecycle counts), `productivity`, `retention` (not contacted, reviews overdue, at-risk clients), `products_per_client` (average and distribution), `compliance` (score, components, gaps).

**Honest numbers.** Rand figures are demo estimates from `radar_config.py` and every block states its formula. `productivity` is an **illustrative model** (tracked activity in the last 30 days multiplied by assumed minutes per task, both listed in the payload), not a stopwatch. `avg_claim_handling_days` is real: the mean of `closed_at - submitted_at` over closed claims (`avg_claim_handling_basis` says over how many).

`GET /clients/{id}/health` (staff, in scope): `{score 0-100, band: healthy|watch|at_risk, components[{key,label,weight,value,points,detail}], last_contact_at, days_since_contact, weakest, formula, at_risk_below}`. The formula is simple and printed: 30 x recent contact + 25 x review up to date + 20 x goals on track + 15 x documents valid + 10 x no stuck claims.

### 5.18 Workflows and notifications

**One config, read by an engine.** `backend/app/domain/workflows.py` defines the motor claim and every client request in the same vocabulary: steps, required documents, validation rules (the request `fields`), status transitions with who may make them, and who is notified. `GET /workflows` serves it so a screen can render itself from it. `GET /requests/types` is the request half of the same data and gained `description`, `steps`, `documents`, `requires_identity`, `insurer_forward` and `sla_days`.

**Adding a simple request type is a config entry**: its fields and an entry in `_REQUEST_META`. No new page (the client form is rendered from `fields`), no new endpoint, no migration (`requests.type` is validated against the config, not a database CHECK; a test adds one through the API).

The claim's `allowed_transitions` (section 5.10) now come from the same config that enforces them.

**Notifications are in-app only.** A status change writes one notification per person to tell (the client and/or their adviser), from the transition's `notify` list in the config: an adviser moving a claim tells the client; a client submitting a claim or a request tells their adviser. There is no email, SMS or push. `GET /notifications?unread=true` returns `{items[{id, kind, title, body, link:{resource, id}, client_id, created_at, read_at}], unread_count}` for the caller only. Screens poll it (about every 8 seconds).

A request now has a **timeline** (`timeline[]` on `GET /requests/{id}`, same shape as a claim's events, `visible_to_client` respected): `created`, `forwarded` (to the simulated provider), `status_changed`, `insurer_update`, `note`.

**Demo controls** (`DEMO_MODE=true`; otherwise both answer `404 not_found` and the server refuses `DEMO_MODE` with `ENVIRONMENT=production`; `GET /meta` returns `demo_mode`):

| Endpoint | Notes |
|---|---|
| `POST /demo/insurer-step` | Body `{claim_id}` or `{request_id}`. The **simulated** insurer (or provider) takes its next step: registers the claim with a `SIM-` number, moves it through assessment, quotes, authorisation, repair and completion; for a request marked `insurer_forward` it acknowledges and then responds. It uses the same code path as an adviser's status change, so the timeline, notifications and audit entry are produced by the engine. Events say "simulated" and have no actor. `409` when it has nothing left to do. An adviser reaches their own clients' items; the owner reaches all. |
| `POST /demo/reset` | Owner only. Puts every data table back to the seeded state (the approved-document library is kept). |

### 5.19 Identity vault

A verified identity document is captured **once**, stored in the private bucket (`identity/<client>/...`, signed URLs only) and **reused** instead of asking the client again, while it is valid. Document types: `id_document`, `drivers_licence`, `proof_of_address`.

**Verification is simulated.** `IdentityVerifier` is an interface; `DemoIdentityVerifier` (`verifier: "demo_simulated"`) contacts no provider and checks nothing about the document except that an entered expiry date is not in the past. Every document object says `is_simulated_verification`, and `GET /identity` carries a `verifier.note`. This is **not** a KYC check.

| Endpoint | Notes |
|---|---|
| `GET /identity` | A client sees their own; staff pass `client_id` (in scope). Returns `documents[]`, `summary` (per type: `state` of `valid`, `expiring` (30 days), `expired`, `pending`, `stale` (proof of address older than 90 days), `missing`), `reuse_log[]` (which claim or request used which document, when, by whom), `verifier`, `rules`. |
| `POST /identity` | Multipart: `doc_type`, `file` (JPEG, PNG, WebP or PDF, checked by content), optional `expiry_date`, and `client_id` when an adviser adds it for a client. Stored as `pending` (`verification_source: "uploaded"`); the adviser is notified. |
| `POST /identity/{id}/verify` | Adviser of the client. Runs the verifier, marks it `verified` (`verified_by`, `verified_at`, `verification_source: "simulated_verification"`), supersedes the previous one of that type, and for a licence keeps `clients.drivers_licence_expiry` in step. `409` if not pending. |
| `POST /identity/{id}/reject` | Body `{reason}`. |
| `GET /identity/{id}/url` | A short-lived signed URL. Each issue is audited (`identity.viewed`). |

**Reuse.** Creating a claim draft attaches the client's valid verified driver's licence (same private object, no copy) and logs the reuse, so `missing_fields` no longer asks for it; `GET /claims/{id}` gains `identity.drivers_licence` (`reused`, `state`, `expiry_date`). Deleting that attachment from a draft never deletes the vault file. A request whose type `requires_identity` reuses the verified ID (a timeline event says so) or records that one is needed; `address_change` reuses a proof of address that is under 90 days old. An expired, pending or missing document is never reused.

**Expiry.** An ID document within 60 days of expiry creates an `identity_expiry` reminder (client and adviser), a compliance-health flag, and an `expiring_document` radar touchpoint. A proof of address creates `proof_of_address_stale` after 90 days.

## 6. End-to-end flows

Numbers are call order. `→` is a client-to-API call. Use TanStack Query (or equivalent) so results are cached and re-fetched sensibly.

### 6.1 Bootstrap after login (both roles)
1. Sign in with Supabase Auth → store the session.
2. → `GET /me` → read `role`.
3. `client` → `GET /me/dashboard`. `advisor` → `GET /advisor/dashboard`.
4. Load `GET /meta` once (needs no token) and cache it.

### 6.2 Report an accident and register a claim (client)
1. Tap "Report an Accident" → `GET /claims/checklist` (instant, cacheable).
2. User starts the claim → `POST /claims` → keep `id`.
3. For each photo/document → `POST /claims/{id}/attachments` (multipart).
4. Form steps → `PATCH /claims/{id}` (send only changed fields). Read `missing_fields` to drive a progress indicator.
5. Final step → `POST /claims/{id}/submit`. On `422`, map `details[].field` to form fields.
6. Tracking screen → `GET /claims/{id}` (poll every 30 s or refetch on focus, see 7.4). Render `timeline` and the status stepper from `GET /meta` → `claim_statuses` using `client_label`.

### 6.3 Work a claim (adviser)
1. `GET /claims/pipeline` → board.
2. Open a card → `GET /claims/{id}`.
3. `PATCH /claims/{id}/insurer-details` (claim number, handler).
4. `POST /claims/{id}/transitions` `{ "to_status": "registered" }` and onward (buttons come from `allowed_transitions`).
5. `PATCH /claims/{id}/hire-car`, `PATCH /claims/{id}/repair-details`, `POST /claims/{id}/updates` as the repair progresses.
6. The client sees each visible change on their next `GET /claims/{id}`.

### 6.4 Ask the assistant (adviser)
1. `GET /documents` → optional filter chips.
2. `POST /assistant/query` → render `answer` and numbered citation chips.
3. Citation click → `GET /documents/{document_id}/url` → open at `#page=<citation.page>`.
4. Follow-up → `POST /assistant/query` with the returned `conversation_id`.

### 6.5 Draft an insurer email linked to a claim (adviser)
1. `GET /email/status` → show the "Demo email" badge.
2. `GET /email/threads?claim_id={id}` → context threads already linked.
3. `POST /email/drafts/generate` → show the draft with `warnings`; the adviser edits and copies it out.

### 6.6 Goals and reminders
- Adviser: `POST /goals`, `PATCH /goals/{id}` (progress updates), `POST /reminders/run-check`.
- Client: `GET /goals`, `GET /reminders`, `POST /reminders/{id}/complete`.

## 7. Frontend integration notes

### 7.1 Supabase Auth
- The frontend uses the Supabase JS client only for authentication (sign in, sign out, session refresh). All data goes through this API. Do not query Supabase tables or storage directly from the browser.
- Send `session.access_token` as `Authorization: Bearer …` on every call. On `401 token_expired`, refresh the session and retry the request once. On `401 token_invalid` or a second `401`, sign the user out.
- Whether the backend verifies tokens locally or by asking Supabase is an internal choice (see `ARCHITECT.md`); it does not change this contract.

### 7.2 Uploads
- Use `FormData` and let the browser set the `Content-Type` boundary; do not set the header manually.
- Upload one file per request and show per-file progress and errors. Convert HEIC to JPEG before upload.
- Signed URLs in `attachments[].url` expire (`url_expires_at`). Do not cache them beyond that; refetch the claim.

### 7.3 Untrusted content
Render as **plain text** (never `innerHTML`): email `body_text`, claim `description` and witness statements, request `client_note`, timeline `message`. Render the assistant `answer` through a Markdown renderer that disallows raw HTML.

### 7.4 Freshness
There is no push channel in v1. On the claim tracking screen, refetch every 30 s while the tab is focused, and always on window focus. Reminders and dashboards refetch on navigation.

### 7.5 Resilience
- **Cold start:** free hosting can put the backend to sleep, so the first request after idle may be slow. Use a generous timeout (60 s) and a loading state for the first call. The team runs the warm-up script before demos.
- **429 / 503 from LLM endpoints:** show a friendly "try again in N seconds" using `retry_after_seconds`.
- **Errors:** always read `error.code` (not the message text) for logic, and show `error.request_id` in a "copy details" affordance.

### 7.6 Language and tone
Client-facing copy is simple and reassuring; adviser-facing copy is efficient. The API supplies role-appropriate status labels (`status_label`, `client_label`/`advisor_label`), the checklist wording and the request field labels. Other copy belongs to the frontend.

### 7.7 Mocking while the backend is being built
Until the backend is deployed, the JSON examples in Section 5 can be used as fixtures. Treat any field in Section 4 as present; treat unknown fields as ignorable.
